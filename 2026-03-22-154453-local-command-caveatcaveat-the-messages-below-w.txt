  Migration Plan: supabase/migrations/20260322000000_create_trades.sql

  1. Trade Status Enum (trade_status)

  Nine statuses covering the full lifecycle:

  ┌───────────────┬───────────────────┬─────────────────────────────────────┐
  │    Status     │       Phase       │               Trigger               │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ pending_offer │ Offer sent        │ Initiator creates trade             │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ negotiating   │ Discussion        │ Counterparty responds               │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ accepted      │ Agreement         │ Both parties agree → fires AI agent │
  │               │                   │  runner                             │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ flagged       │ AI gate           │ Safety agent returns block          │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ scheduled     │ Logistics         │ Logistics agent sets time +         │
  │               │ confirmed         │ location                            │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ in_progress   │ Active handoff    │ Either party confirms exchange      │
  │               │                   │ started                             │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ completed     │ Terminal          │ Both confirm success                │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ cancelled     │ Terminal          │ Either party withdraws before       │
  │               │                   │ in_progress                         │
  ├───────────────┼───────────────────┼─────────────────────────────────────┤
  │ disputed      │ Terminal          │ Problem reported after in_progress  │
  └───────────────┴───────────────────┴─────────────────────────────────────┘

  2. trades Table Columns

  - Identity: id UUID PK, created_at, updated_at
  - Parties: initiator_id UUID → auth.users, counterparty_id UUID → auth.users
  - Listing: listing_id UUID (bare — FK to listings added in a later migration
  once that table exists)
  - Status: status trade_status NOT NULL DEFAULT 'pending_offer'
  - Terms: agreed_terms TEXT (frozen at accepted)
  - AI Moderation (from safety.ts agent): moderation_verdict TEXT CHECK 
  ('allow','block','review'), moderation_confidence NUMERIC(4,3),
  moderation_reasoning TEXT, moderated_at TIMESTAMPTZ
  - Vibe (from vibe.ts agent): vibe_score SMALLINT 0–100
  - Logistics (from logistics.ts agent): logistics_data JSONB (flexible shape),
  scheduled_at TIMESTAMPTZ (denormalized from JSONB for fast range queries)
  - Terminal context: cancellation_reason TEXT, dispute_reason TEXT
  - Phase timestamps: accepted_at, completed_at, cancelled_at
  - Constraint: CHECK (initiator_id <> counterparty_id)

  3. Indexes

  - (initiator_id, status, created_at DESC) — "my trades" query
  - (counterparty_id, status, created_at DESC) — "trades on my listings"
  - (listing_id, status) — "active interest on a listing"
  - Partial unique (listing_id) WHERE status IN ('in_progress','completed') —
  enforces at most one active/completed trade per listing
  - (status, moderated_at) WHERE status = 'flagged' — moderation review queue
  - (updated_at DESC) — incremental sync

  4. set_updated_at Trigger

  A BEFORE UPDATE trigger calling a shared set_updated_at() function to keep
  updated_at current automatically.

  5. Row-Level Security

  ┌───────────────────────────┬───────────┬──────────────────────────────────┐
  │          Policy           │ Operation │               Rule               │
  ├───────────────────────────┼───────────┼──────────────────────────────────┤
  │ trades_select_participant │ SELECT    │ auth.uid() IN (initiator_id,     │
  │                           │           │ counterparty_id)                 │
  ├───────────────────────────┼───────────┼──────────────────────────────────┤
  │ trades_insert_initiator   │ INSERT    │ auth.uid() = initiator_id        │
  ├───────────────────────────┼───────────┼──────────────────────────────────┤
  │ trades_update_participant │ UPDATE    │ Either party, only when status   │

  ├───────────────────────────┼───────────┼──────────────────────────────────┤
  │ trades_no_user_delete     │ DELETE    │ USING (false) — immutable audit  │
  │                           │           │ trail; use cancelled instead     │
  └───────────────────────────┴───────────┴──────────────────────────────────┘

   negotiating) are not enforced in SQL — they live in actions/trades.ts as a
  TypeScript state machine for testability.

  A new "Agent Conventions" subsection added under ## Conventions:

  ### Agent Conventions
  - **Single Groq entry point**: All agents call Groq exclusively through
    `lib/agents/groq-client.ts`. No agent imports the Groq SDK directly.
  - **Agent signature**: Every agent exports one async function —
    `run<AgentName>(input: <AgentName>Input): Promise<<AgentName>Output>`.
    Inputs and outputs are named interfaces, not inline types.
  - **No DB access in agents**: Agents are pure inference functions.
    DB writes from agent results happen in `actions/` Server Actions only.
  - **JSON output contract**: Every agent instructs the model to return
    a JSON object. If JSON parsing fails, the agent returns a safe default
    (`verdict: 'review'`, `confidence: 0`) — it never throws a parse error.
  - **PII in prompts**: Strip or redact `initiator_id`, `counterparty_id`,
    and any user-identifying fields before passing content to Groq.
    Only `trade_id` may be forwarded for audit correlation.
  - **Tests**: Every agent has a co-located `__tests__/<agent>.test.ts`.
    Mock `groq-client.ts` via `vi.mock`; never make live API calls in tests.
    Include at least one LLM-as-judge eval test that scores the agent's
    `reasoning` field for quality.
